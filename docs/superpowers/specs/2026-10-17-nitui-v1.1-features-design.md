# nitui v1.1 feature set — design

Date: 2026-10-17. Approved scope: everything proposed in chat (features 1–4 and extras 1–9).

## Ground rules

- Every feature is available as a scriptable CLI command **and** in the TUI where it makes sense.
- Endpoint shapes come from the official Nitrapi-PHP SDK. Anything not confirmed against a live account is marked **(unverified)** and must degrade gracefully (clear error, never a crash or silent no-op). The hidden `nitui debug api` command is the tool for verifying shapes later.
- Tests use `httptest` servers and the existing `NITUI_CONFIG_DIR` / `apiBaseURL` seams. No real network in tests.
- Polling/timing code takes an injectable interval so tests run instantly.

## 1. Live status (`internal/api/wait.go`, TUI + CLI)

`WaitForStatus(ctx, fetch func(ctx) (*GameServer, error), opts WaitOptions) (*GameServer, error)`

- `WaitOptions{Want func(status string) bool; LeaveFirst string; Interval, GracePeriod time.Duration; OnPoll func(*GameServer)}`.
- Restart: want `started`, `LeaveFirst: "started"` — the server must be seen leaving `started` before `started` is accepted, **unless** `GracePeriod` (default 20s) elapses without a change, in which case a still-`started` server is accepted (restart finished faster than our polling).
- Stop: want `stopped`. Context deadline (default 5 min) yields a `*TimeoutError` naming the last seen status.
- TUI: after restart/stop the model enters a `waiting` state; a `tea.Tick` every 3s issues a status fetch; the detail view shows the live status and a "waiting for X…" line; completes with a success status message. A passive 10s refresh runs on the detail screen at all times (single tick chain, restarted on entering the screen, ignored when stale via a generation counter).
- CLI: `server restart|stop --wait`, `server status --watch` (prints on change, Ctrl-C to quit).

## 2. Server settings (`internal/api/settings.go`)

- `GameServer.Settings map[string]map[string]any` parsed from the gameserver payload's `settings` object (category → key → value). `GetSettingsDefaults` → `GET …/gameservers/settings/defaults`. `SetSetting(category, key, value)` → `POST …/settings` `{category,key,value}`. `ResetSettings` → `DELETE …/settings`.
- Values are `any`; display via `fmt.Sprint`; on write send the value as a string (Nitrado's own panel does) **(unverified: type handling for booleans/numbers)**.
- CLI: `settings list [category]`, `settings get <category> <key>`, `settings set <category> <key> <value>`, `settings reset --yes`. `list` flags values differing from defaults.
- TUI: screen `settings` (category list) → `settingsKeys` (key list with current/default) → inline `textinput` edit. After a successful write, offer "restart now? (y/n)".

## 3. Updating server files

Two separate pieces:

- **Update status/trigger (spike, may be dropped):** parse `game_specific.update_status` and show it on the detail screen. Add `server update` which restarts the server and waits (hypothesis: Nitrado updates the game on start). **(unverified)** — the command's help text says so, and the README lists it under Known gaps until confirmed.
- **File manager (extra 6):** `internal/api/files.go` wraps the file-server API: list (`GET …/file_server/list?dir=`), download (`GET …/file_server/download?file=` → token+url → GET), upload (`POST …/file_server/upload` → token+url → POST), delete, mkdir, move. CLI: `files ls|cat|get|put|rm|mkdir`. TUI: file browser screen (navigate, view/edit small text files via `$EDITOR`-free inline preview, delete with confirm).

## 4. Update notification (`internal/update`)

- `Check(ctx, current string) (*Release, error)`: GET `https://api.github.com/repos/ShifuRain/Nitrado-TUI/releases/latest`, compare semver (strip `v`; `dev` builds skip).
- Cache `{checked_at, latest}` in `update_check.yaml` in the config dir; refetch at most every 24h; failures are silent (never delays or breaks anything; 3s timeout, run in a goroutine / `tea.Cmd`).
- TUI: one-line banner under the content. CLI: a stderr note after successful commands (suppressed for `--json`, non-TTY stderr, and completion/version commands).
- Opt-out: `update_check: false` in config.yaml or `NITUI_NO_UPDATE_CHECK=1`.
- Message includes install-method hint (winget / AUR / release URL). No self-update.

## 5. Extras

1. **Confirm prompts:** TUI `y/n` modal state before stop/restart/uninstall/reset; CLI `--yes` required when stdin is not a TTY, otherwise prompt.
2. **Richer detail:** show service name (from `Service.Details.Name`) instead of `Server <id>`; add memory, location, FTP user/host, update status; `GET …/gameservers/stats` summarized as latest CPU/RAM (CLI `server stats`) **(unverified shape — parse defensively)**.
3. **Stop/restart message:** `--message` flag; TUI prompts for an optional message. Sent as `message` and `restart_message`/`stop_message`.
4. **Backups:** `internal/api/backups.go` — `GET/POST/DELETE …/backups`, restore via `POST …/backups/extract`. CLI `backups list|create|delete|restore`. TUI list screen with `c` create, `enter` restore (confirm), `d` delete (confirm).
5. **Console/logs:** `command` sends via `POST …/gameservers/command {command}`. `logs` shows `GET …/gameservers/admin_logs`. TUI console screen: input line + scrollback of sent commands/responses.
6. **File browser/editor:** see §3.
7. **Game management:** wire `StartGame`/`UninstallGame` into CLI (`games start|uninstall`) and the TUI picker (`enter` = install/switch or start if installed, `u` = uninstall w/ confirm). Resolves the README "install vs start" gap by choosing start for installed games.
8. **`--json` + completions:** persistent `--json` flag on list/status/get-style commands emitting stable JSON; Cobra's built-in `completion` command stays enabled.
9. **`--server <id>` flag:** persistent flag on `server`, `settings`, `files`, `backups`, `games`, `command`, `logs`; overrides the selected server for one invocation.

## Architecture notes

- `internal/tui` is split by screen: `update.go` (dispatch) plus `screen_<name>.go` files holding each screen's model fields, key handling, and view. Shared helpers (confirm modal, spinner/footers) live in `common.go`.
- `internal/cli` gets one file per command group; a `resolveServer(cmd)` helper honors `--server` then state.
- `api.Client` stays one type; new endpoint groups are added as methods in new files.
- Error handling: API errors go through `apiErr`/`FriendlyMessage`; waiting timeouts are distinct typed errors.

## Delivery order

1. Foundation (`--server`, `--json`, confirm helper, richer types) 2. Live status 3. Update notification 4. Settings 5. Game management 6. Backups 7. Files 8. Console/logs 9. Update spike + stats 10. README/docs.
